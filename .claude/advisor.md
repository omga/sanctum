# The advisor — design

Plan for `roadmap.md` §2. Nothing here is built yet.

The feature: **an astrologer you can ask questions, answering from your
actual computed chart rather than your star sign**, reached from the
screens that already provoke the question — a compatibility reading, a
relationship report, today's transit.

`roadmap.md` §2 argues the *why* and the commercial shape. This file is
the *how*: the layers, the types, the order to build them in, and the
decisions that are hard to reverse later.

---

## 1. The constraint that shapes everything else

`handoff.md` §3: the privacy promise survives analytics and survives
RevenueCat's anonymous IDs, and **it does not survive AI chat**.

The promise is exact, and it is the thing to protect:

> "No account, ever. Your name, your birth date and your journal stay on
> this phone."

That sentence stays true if — and only if — the advisor sends **computed
positions and the question, and nothing else**. Not the name. Not the
birth date. Not journal text. The chart is derivable from the positions;
the model does not need the date that produced them.

### Enforce it in the type system, the way analytics already is

`AnalyticsEvent` has a private constructor and ~23 named constructors,
and the reason is stated plainly in `handoff.md`: *call sites cannot leak
personal data because no constructor accepts any*. The advisor payload
gets the same treatment.

```
domain/models/advisor_context.dart

final class AdvisorContext {
  const AdvisorContext._({...});          // private

  factory AdvisorContext.forMatch(CompatibilityMatch match);
  factory AdvisorContext.forReport(RelationshipReport report);
  factory AdvisorContext.forToday(TransitReading reading);
}
```

Every field is a number, an enum, or a bundled-content id: ecliptic
longitudes, aspect kinds, orbs, facet scores, element pairs, the moon
phase. **There is no `String name` field and no `DateTime birthDate`
field anywhere in the type**, so a call site cannot pass one by
accident and a future contributor cannot add one without deleting this
paragraph first.

`advisor_context_test.dart` mirrors `analytics_test.dart`: a denylist of
field names, a primitives-only check, a length check that would catch
prose, and an exhaustive list of every constructor. The list is the
guarantee; keep it complete.

### Names live on the device and never leave it

The nudge the user wants says **"You + Alex"**. That is right, and it is
free: the name is already on the phone, the notification is already
composed on the phone (`ReminderService` carries whole sentences because
nothing of ours runs at fire time), and the chat UI renders on the phone.

So: the *prompt* says `them`. The *screen* says `Alex`. The proxy and
the model never see the string. When the answer comes back referring to
"them", a local substitution pass rewrites it to the stored name before
it is painted.

This is worth doing properly rather than approximately, because it is
the whole differentiation: every competitor sends the name, and none of
them can say this sentence.

**Built:** `MessageRedaction` (`domain/services/`). The type system
covers the computed half of a request; it cannot cover a text box, and
the first thing anybody asks is "why does Alex keep doing this". So
outbound text has the names the app already stored rewritten out of it —
the other person becomes "them", the user becomes "me", matching is
whole-word and case-insensitive and works in Cyrillic. `containsAny` is
the assertion the send path runs before handing anything to a transport.

Starters avoid the problem rather than solving it: each has a
`displayKey` carrying `{name}` and a `promptKey` that never does, so the
question the user reads and the question that is sent are two written
strings rather than one string and a regex.

### Consent is a screen, not a checkbox

First open of any advisor surface, before a single byte moves:

- what leaves the device (positions, aspects, scores, your question)
- what does not (name, birth date, journal, anything from other screens)
- who receives it (the proxy, then the model vendor — named)
- how long it is kept (see §5: nothing is stored server-side)
- that the answer is generated by an AI — **EU AI Act Art. 50**, which
  was scheduled to apply from 2 August 2026 with the timeline under
  discussion; confirm status with counsel before shipping to an EU
  locale

Declined is a real state that persists and is re-offerable, not a dialog
that reappears every launch. Stored next to the other one-shot flags in
`SettingsRepository`.

The privacy policy, the store data-safety declaration and the onboarding
copy change **in the same commit** as the first real network call.
`README.md` also currently opens with "There is no backend and no
account" — half of that stops being true here.

## 2. Domain model: built for two transports from day one

The stated requirement is that this is reusable for real person-to-person
chat later. That is cheap if the domain never learns who is answering,
and expensive to retrofit if it does.

```
domain/models/conversation.dart

enum ConversationKind { advisor, person }   // drives disclosure + gating

class Conversation {
  final String id;
  final ConversationKind kind;
  final ConversationSubject subject;        // what it is about
  final DateTime startedAt;
  final int turnsUsed;
}

sealed class ConversationSubject {}         // the reuse seam
final class MatchSubject   extends ConversationSubject { final String matchId; }
final class ReportSubject  extends ConversationSubject { final String matchId; }
final class DaySubject     extends ConversationSubject { final CalendarDate date; }
final class OpenSubject    extends ConversationSubject {}

class ChatMessage {
  final String id;
  final String conversationId;
  final MessageAuthor author;   // .you | .counterpart
  final String body;
  final DateTime at;
  final MessageStatus status;   // sending | sent | failed
}
```

`MessageAuthor.counterpart` rather than `.advisor` is the point: a
person-to-person build swaps the transport and the `kind`, and every
widget, view model, table and test below keeps working unchanged.

`ConversationKind` exists because two things *must* differ: an advisor
conversation shows the AI disclosure and is gated on credits/purchase; a
person conversation shows neither. Nothing else in the model branches
on it.

### The transport interface

```
domain/services/chat_transport.dart

abstract interface class ChatTransport {
  Stream<ChatChunk> send({
    required Conversation conversation,
    required List<ChatMessage> history,
    required AdvisorContext? context,
  });
}
```

Three implementations, in build order:

| | what it is | why |
|---|---|---|
| `ScriptedChatTransport` | canned replies, artificial delay | builds and tests the entire UI with no proxy, no key, no cost |
| `ProxyChatTransport` | HTTPS to our proxy, streaming | the real thing |
| *(later)* `PeerChatTransport` | whatever P2P becomes | the reason for this interface |

Streaming is in the interface from the start. Retrofitting token-by-token
rendering onto a `Future<String>` means rewriting the view model, and
the perceived-latency difference is most of whether chat feels alive.

## 3. Where the code goes

Unchanged rule: `features/ → domain/ ← data/`, and `domain/` imports
nothing but pure Dart.

```
domain/
  models/     conversation.dart, advisor_context.dart
  services/   chat_transport.dart          (interface only)
              conversation_budget.dart     (turn caps, pure)
              conversation_gate.dart       (may they open one?)
              advisor_prompt_trigger.dart  (when to nudge, pure)
              conversation_starters.dart   (which questions to suggest)
data/
  repositories/ conversation_repository.dart   (Drift)
  services/advisor/ proxy_chat_transport.dart
                    scripted_chat_transport.dart
features/
  advisor/    view/ + view_model/
```

Note what is pure and therefore cheap to test: the budget, the gate, the
trigger and the starter selection. That is most of the product logic and
none of it needs a network, a key or a device — which is the same reason
`PaywallTrigger` could be pinned by a two-year simulation.

## 4. Triggers — "You + Alex → why does he not care?"

This is the retention mechanic, and it is also the fastest way to make
the app feel like spam. `PaywallTrigger` already solved the same problem
and its rules should be copied deliberately, not reinvented:

- never on install day
- **explicit intent always wins** — tapping "Ask about this" bypasses
  every cooldown
- otherwise an *earned moment* is required
- each ignored nudge pushes the next one out: 3 → 7 → 14 → 30 days
- after 4 ignored, it never nudges automatically again

For the advisor, an earned moment is a computed fact the user has
already seen and has an obvious question about:

| moment | the question it generates |
|---|---|
| a match with a facet ≤ 40 | "Why is Trust only 43?" |
| `pull.them` / `pull.you` strongly leaning | "Why do I keep thinking about this?" |
| `power.them` strong | "Why does it always end up their way?" |
| a report bought in the last 48h | "Ask anything about you and {name}" |
| a hard transit to natal Venus today | "What is this about today?" |

`ConversationStarters` is a pure function from that state to a ranked
list of suggested questions, localised through `CopyBook` like every
other string. **They are suggestions, not the only input** — the text
field is always there.

Delivery reuses `ReminderService` exactly as-is: the nudge is composed
now, carries its own copy, and is scheduled inexactly. One consequence
worth stating — a nudge naming a person must be composed on-device
(§1), which the existing service already forces by construction.

Entry points, in descending order of how well they convert per
`roadmap.md` §2: the report footer, the compatibility result screen, the
transit panel. A question the user already has beats a blank box.

**There is also an Ask tab**, added after seeing the feature on a device
— the contextual cards are at the foot of screens a user has to scroll
to, so nobody who has not already found them learns the feature exists.
It is discovery, not the primary route in, and it is deliberately *not*
a blank chat: the tab is a list of pairings, every route out of it is
attached to one, and there is no composer until a subject is chosen. The
empty state sends people to the compatibility tab rather than offering a
subjectless conversation, because a reading with no pairing behind it is
the generic wrapper this whole design exists not to be.

## 5. The proxy — the first backend this app has had

Non-negotiable: the model API key cannot ship in the binary.

Smallest thing that works:

- one HTTPS endpoint, streaming (SSE), stateless
- **stores nothing.** History lives on the device and is re-sent, capped
  and trimmed, each turn. This is not a storage optimisation — it is how
  "no conversation history on a server the app cannot delete from"
  becomes true by construction rather than by policy
- verifies entitlement before spending inference: a RevenueCat receipt
  or webhook-derived token, not a client claim
- rate limits per install and globally; a runaway client must not be
  able to spend the month's budget
- rejects any payload that fails the same schema `AdvisorContext`
  serialises to — the server should refuse a name even if a future
  client bug sends one
- logs metadata only: latency, tokens, error class. Never prompt bodies

The system prompt lives server-side, so it can be corrected without a
store release. The chart data comes from the client, because the client
is the only thing that has it.

## 6. Money — recommendation

`roadmap.md` §2 argues credits over bundling into the subscription and I
would not reopen that. But it also says **build the economy last**, and
that argument applies to the advisor's own first release:

> A ledger is infrastructure — balances, top-ups, expiry, refunds,
> restores on a second device — and none of it answers whether anybody
> wants to ask an astrologer anything.

**Recommendation: sell a conversation, not a currency, for v1.**

- one purchase = one conversation about one subject, capped at N turns
  (start at 10 exchanges; it is a number, tune it)
- priced in real money, which is what `roadmap.md` §2 argues for anyway:
  "price reports in money and chat in credits" — and there are no
  credits yet
- ownership is recorded exactly like a report: a subject id in a set,
  "owned stays owned", re-opening a finished conversation to *read* it
  is free forever. Only new turns cost
- subscribers get one conversation a month included — the same mechanic
  as the included report, for the same reason: it forms the habit and
  makes the subscription drive the purchase rather than replace it

This reuses the consumable purchase path already shipped and verified
for the report, needs no ledger, and keeps the cost exposure bounded per
sale, which "unlimited chat for an hour" does not.

Credits become the right answer the day there is a second variable-cost
thing to spend them on. `ConversationGate` is where that decision lives,
so switching later touches one pure file and its tests — not the UI, not
the transport, not the storage.

## 7. Storage

**Built.** Conversations and messages go in **Drift**, not
`SharedPreferences`.
They are rows, they are queried by conversation, they grow without
bound, and one of them will eventually need a cascading delete. That is
a `schemaVersion` bump to 2 and the first real migration this database
has had — write it with `beforeOpen`'s foreign-keys pragma in mind,
since deleting a conversation must take its messages with it.

*Ownership* of a conversation stays in `SharedPreferences` beside the
owned-report ids, because it is a small set of strings read at gate time
and it must survive a database wipe.

"Delete this conversation" is a first-class feature, not a settings
afterthought. The journal already learned this lesson (`handoff.md`: a
journal you cannot delete from is a worse product than one that never
offered it), and a chat about a named person is more sensitive than a
journal entry, not less.

## 8. Build order

Deliberately: **functionality first, money last**, and no network until
the shape is right.

1. ~~**Domain + scripted transport.**~~ **Done.** Models, gate, budget,
   starters, redaction, `ScriptedChatTransport`. 70 tests, no network,
   no key, no cost. `AdvisorFailure` was added to the sealed `AppFailure`
   set with a `kind`, because the screen has to tell "you are offline"
   from "you have asked a lot in a short time".
2. ~~**The UI.**~~ **Done.** Conversation screen, streaming render,
   suggestion row, failure and retry, spent state, entry cards on the
   reading and the report. Runs entirely on the scripted transport.
   Copy shipped in all four locales. Verified on an iPhone 17 Pro
   simulator, including the software keyboard, which is what the widget
   tests cannot see.

   Two things that only running it revealed, both fixed: the suggestion
   row showed a single generic chip on an ordinary pairing, because
   every diagnostic threshold was correctly declining to fire — so
   `ConversationStarters` now tops the row up with questions that are
   specific but imply no problem. And the highest facet is picked
   ignoring Drama, because `report.mechanism.drama` says in as many
   words that a high one is not a compliment.
3. ~~**Storage.**~~ **Done.** Drift tables, the first real migration
   (`schemaVersion` 1 → 2, additive), delete with a cascade, history
   trimming. The migration test builds a version 1 database by hand and
   proves a journal written before the upgrade is readable after it —
   that is the only thing that actually matters here.
4. **The proxy.** Deploy, then `ProxyChatTransport`. One provider flag
   swaps it for the scripted one; keep both forever, because the
   scripted one is how the widget tests stay fast and deterministic.
5. **Consent + disclosure + policy + data-safety.** Ships with, or
   before, step 4 reaching a real user.
6. **Purchase and gating.**
7. **Triggers and notifications.** Last on purpose: nudging people
   toward a feature is the wrong thing to tune before the feature is
   known to be good.

Steps 1–3 are the reusable half. If person-to-person chat ever happens,
it starts at step 4 with a different transport.

## 9. What must be true before it ships

- `advisor_context_test.dart` is exhaustive and passing
- a test asserts the outbound payload for a real match contains no
  substring of the person's name — belt and braces over the type system
- the proxy refuses an over-long or unknown-field payload
- the AI disclosure is visible in the conversation UI, not only in
  onboarding
- privacy policy, store data-safety, `README.md` and the onboarding
  copy all updated in the same change
- `analytics.md` gains its events, **with call sites in the same
  commit** — six declared events already fire from nowhere

## 10. Open questions

1. **Model vendor and hosting.** Affects cost per turn, latency, and
   what the consent screen names.
2. **Turn cap.** 10 is a guess. It sets both the price and the cost
   ceiling.
3. **Does a conversation expire?** Recommendation: the *turns* are
   spent, the *transcript* is permanent. No expiry, matching the report.
4. **iOS purchase path is still unverified against the real App Store**
   (`handoff.md`) — that blocks selling anything on iOS, advisor
   included.
5. **Language.** The advisor must answer in the user's chosen locale;
   that is a system-prompt instruction plus an eval, not a code path.
